# RemoteX Protocol (M0)

This document describes the initial, versioned data model. It is not yet a
network protocol implementation. M1 will define framing, authentication, size
limits, and QUIC behavior around these types.

## Compatibility

Every `MessageEnvelope` carries a protocol version. The M0 version is `1`.
Receivers must reject unsupported versions rather than guessing. New optional
fields may be introduced compatibly; semantic or framing changes require a new
version.

Serialization uses `serde`. Bincode is used only in unit tests to prove a compact
binary round trip; M1 will freeze the wire codec and framing format.

## Identifiers

- `SessionId` is a UUID generated by the control server.
- `DeviceId` is a server-issued nine-digit value represented as a validated
  string so leading zeroes remain meaningful.
- `TransferId` is a UUID scoped to a file-transfer operation.

Identifiers are opaque. Clients must not derive authorization decisions from
their contents.

## Logical channels

| Value | Channel | Direction |
| ---: | --- | --- |
| 0 | Control | Bidirectional |
| 1 | Video | Agent to controller |
| 2 | Input | Controller to agent |
| 3 | Clipboard | Bidirectional |
| 4 | File transfer | Bidirectional |
| 5 | Audio | Reserved |
| 6 | Telemetry | Reserved |

M0 models all reserved values but implements no channel behavior.

## Envelope

```text
MessageEnvelope {
    version: u16,
    session_id: SessionId,
    channel: Channel,
    sequence: u64,
    timestamp_ms: u64,
    message: Message,
}
```

`sequence` is monotonically increasing within a logical channel and direction.
`timestamp_ms` is milliseconds since the Unix epoch and is informational; it is
not used alone for authentication or ordering.

`Message` is a tagged union of `ControlMessage`, `InputEvent`,
`ClipboardMessage`, and `FileTransferMessage`. The video channel value is
reserved, but its payload model and handling are deferred.

## Control messages

- `SessionRequest { device_id }`
- `SessionAccepted { permissions }`
- `SessionRejected { reason }`
- `SessionEnded { reason }`
- `Ping { nonce }` / `Pong { nonce }`

Permissions separately gate desktop viewing, input, clipboard, file upload, and
file download. Acceptance never implies permissions not present in its value.

## Input events

Input events describe intent and do not contain Windows-specific scan codes:

- absolute normalized pointer movement;
- mouse button down/up;
- vertical/horizontal wheel delta;
- key down/up using a platform-neutral USB HID usage value.

Normalized pointer coordinates are unsigned 16-bit values covering the selected
display. Concrete platform adapters perform coordinate and key translation.

## File-transfer messages

The default chunk size is 4 MiB.

- `Start` declares metadata, total size, chunk size, destination, and SHA-256.
- `Chunk` carries the transfer ID, byte offset, checksum, and bounded bytes.
- `End` declares the final size and SHA-256.
- `Progress` reports the next expected offset.
- `Pause`, `Resume`, and `Cancel` control transfer state.
- `Error` reports a typed transfer failure without leaking local internals.

The receiver validates transfer identity, offsets, declared lengths, chunk size,
and checksums before committing data. M0 implements only pure state validation;
it performs no filesystem I/O.

## Limits for later enforcement

M1 must set and enforce a maximum frame size before allocating payload buffers.
File chunks must never exceed the negotiated chunk size. Strings and rejection
reasons also need explicit encoded-length limits at the transport boundary.
