# RemoteX v1.3.0 implementation plan

Status: implementation plan, 2026-08-13  
Theme: Connectivity & Experience  
Baseline inspected: v1.2.2 (`22b8de6`)

This plan records the behavior found in the v1.2.2 source before describing any
v1.3 changes. It is intentionally narrower than a full ICE/WebRTC redesign.

## 1. v1.2.2 behavior found during inspection

### Control and authorization

- The Control Server owns device presence, explicit session authorization,
  one-time role-bound Relay credentials, the application E2EE session key, and
  session audit start/end records.
- Agent candidates originate in the signed device heartbeat and are copied into
  the authorized controller's `SessionCredentials`.
- Candidate addresses do not authorize a connection. Direct QUIC additionally
  uses an HMAC proof bound to the Session ID, peer role, fresh client/server
  nonces, and the session key.
- Session credentials expire (five minutes by default), and the Agent's token
  and E2EE key are consumed when it claims an accepted session. There is no
  scoped recovery credential or endpoint for reconnecting an active session.

### Candidates and direct QUIC

- `ConnectivityCandidateKind` has only `Lan` and `ServerReflexive`.
- A configured public endpoint is currently represented as
  `ServerReflexive`; the wire model has no candidate ID, creation time, or
  expiry.
- The Windows Agent gathers one host address using a UDP route lookup (or an
  environment override) and may add a manually configured public address.
- There is no standards-compliant STUN query or RemoteX endpoint-observation
  service. The Controller does not publish session-scoped candidates.
- Candidates are validated, sorted LAN-first and then by priority, and tried by
  the Controller. The direct Agent QUIC endpoint is created for the individual
  authorized session rather than kept alive for presence/NAT mapping refresh.

### Relay rendezvous and path selection

- The Controller and Agent first connect to the Relay and wait for `PeerReady`.
- Both sides then spend up to three seconds attempting/accepting direct QUIC.
  The session is not exposed as usable until this attempt completes, even
  though Relay is already ready.
- If direct authentication succeeds, both processes discard their Relay
  transport and use the direct transport. Otherwise, they use Relay.
- `ConnectivityState` exists in the transport crate but is not a complete,
  shared path-selection state machine and is not exposed as a stable frontend
  model.
- `ConnectionType::{Lan, Direct, Relay}` is reported to the Control Server only
  when the session starts/ends. No live Direct-to-Relay switch exists.

### Session lifecycle and recovery

- `Connection` exposes `send`, `receive`, and `close`; it has no path identity,
  statistics, recovery, or migration operation.
- Any transport receive/send failure ends the session. There is no bounded
  retry loop for Wi-Fi interruption, address changes, VPN changes, wake, or a
  transient Control/Relay failure.
- Explicit disconnect sends a disconnect message, releases held input, and
  ends the session. This behavior must remain terminal in v1.3.
- XChaCha20-Poly1305 nonces are direction-separated and derive from Session ID
  plus a monotonically increasing message sequence. Receivers require the exact
  next sequence. A path switch must therefore preserve the same live cipher and
  sequence state and must not replay queued messages.

### Video adaptation and diagnostics

- Video has three adaptive encoder levels with bounds derived from the Agent's
  configured maximum FPS. Three poor samples reduce quality and six good
  samples raise it.
- The adaptation inputs include RTT, packet loss, send-queue pressure, decode
  latency, and render latency in the wire model. In the desktop implementation,
  RTT, packet loss, and render latency are currently sent as zero; queue
  pressure is estimated from decode time. These zeroes are not real
  measurements.
- Source timestamps, capture/encode/decode timings, frame size, FPS, bitrate,
  codec, and frame counts reach the binary Tauri video channel. The WebView
  uses latest-frame replacement and reports receive/render/drop counts.
- Cross-machine frame age is derived from independent wall clocks and is not a
  reliable measured E2E value without clock calibration.
- The Ctrl+Shift+D overlay shows a subset of IPC/render metrics. It does not
  show a typed path, transport, bitrate, RTT, queue pressure, metric provenance,
  or a connection quality calculation. The regular active-session UI does not
  identify P2P versus Relay.

### Relay limits and observability

- Relay memory is bounded by connection, pending-session, frame-size, and
  per-peer outbound-channel limits. Defaults include 1024 connections, 512
  pending sessions, a 32-message queue, five-second heartbeats, and a
  30-second peer timeout.
- Oversized frames, slow consumers, duplicate roles, inactive peers, and
  invalid credentials are rejected; integration tests cover core pairing,
  timeout, encrypted video/input, and file traffic.
- The Relay removes the entire pair when either peer leaves, so the same Relay
  pair cannot currently be transparently rejoined.
- Structured logs cover authentication, readiness, timeouts, and close, but the
  connection-received log includes a full remote address. There are no
  aggregate counters for bytes, outcomes, upgrade latency, or session duration.

## 2. v1.3 architecture decisions

### Fast usable Relay, direct upgrade after readiness

Relay remains the guaranteed authorized path and becomes usable immediately
after rendezvous. Direct checks run with a short, bounded budget without
delaying the initial connected UI. A successful authenticated direct path may
replace Relay only at a controlled message boundary.

The first v1.3 correctness target is automatic **Direct to Relay failover**.
Relay-to-Direct re-upgrade is permitted only if both peers can coordinate a
barrier that cannot reorder non-video traffic. If that barrier is not proven in
tests, re-upgrade remains documented follow-up work; the product must not claim
transparent bidirectional migration.

### Conservative endpoint discovery

Use standards-compliant STUN Binding discovery rather than inventing a new
protocol or cryptography. The Agent queries an explicitly configured/self-hosted
STUN endpoint from the same UDP socket that its persistent QUIC endpoint will
own. This preserves the observed NAT mapping. A STUN response supplies an
address only; it grants no authority.

Candidate kinds become:

- `Host`: local/listening endpoint;
- `ServerReflexive`: short-lived endpoint observed by STUN;
- `ConfiguredPublic`: operator-supplied public mapping.

Each candidate carries a stable per-gather ID, priority, creation time, and
optional expiry. Expired candidates are rejected before use. The priority order
is LAN-capable Host, ServerReflexive, ConfiguredPublic, then Relay. Address
details remain local and are not included in normal server logs or aggregate
metric labels.

For v1.3, RemoteX implements deterministic, ICE-lite-like checks rather than
full ICE: gather, authenticated session exchange, rank, bounded parallel check,
authenticated QUIC handshake, then Relay fallback. Symmetric NAT and networks
that block UDP remain expected Relay cases.

### Explicit path and reconnect state

The transport layer will own one typed state model:

`Negotiating -> RelayConnected -> DirectChecking -> DirectConnected`

with transitions to `RelayFallback`, `Reconnecting`, or `Failed`. A separate
sanitized UI snapshot contains only path kind, QUIC transport, candidate kind
when locally appropriate, timestamps, quality, and setup timings. It never
contains credentials, proofs, or keys.

Reconnect uses bounded exponential backoff with jitter (nominally 500 ms, 1 s,
2 s, 4 s, and 8 s, capped by the active session expiry/recovery lifetime).
Explicit user disconnect, permission revocation, Agent rejection, or normal
session end cancels all retry work.

### Secure session recovery

One-time setup credentials will not be made reusable. If Relay rejoin requires
Control changes, the Control Server issues separate random recovery credentials
scoped to Session ID, role, expiry, and the already accepted authorization.
They are kept in memory by clients, rotated or consumed on recovery, and
invalidated on explicit disconnect, authorization revocation, timeout, Agent
rejection, or session end. Recovery never creates or broadens permissions and
never bypasses a new interactive authorization requirement.

E2EE ciphers and direction sequences survive a transport reconnection for the
same active session. Stale queued video may be discarded; ordered control,
clipboard, input-release, and file-transfer messages must cross an explicit
barrier or cause a clean session restart rather than silent reordering.

### Honest telemetry

Every diagnostic value is tagged internally as `Measured`, `Estimated`, or
`Unavailable`. The UI renders unavailable values as an em dash. Zero is shown
only when zero was measured.

- Capture/encode/decode/render timing, encoded bytes, resolution, codec, and
  receive/render/drop counters are measured at their existing boundaries.
- QUIC RTT is measured from transport statistics when the API exposes it.
- Queue pressure is measured from bounded queue occupancy where possible and
  otherwise explicitly estimated.
- Packet loss is shown only when a defensible QUIC statistic is available.
- Cross-machine frame age remains unavailable until clock offset/uncertainty is
  calibrated; same-clock IPC age may be labeled estimated and kept separate.

The active-session quality grade combines RTT, queue pressure, recent frame
replacement/drop ratio, frame-age evidence when available, and connection
stability. Bitrate alone never determines quality.

## 3. Implementation phases

### Phase A — foundation

- Expand and validate the candidate wire model, including expiry and duplicate
  handling, with compatibility-focused protocol tests.
- Replace the unused connectivity enum with a tested path-selection state
  machine and sanitized UI event/snapshot types.
- Add setup timestamp and diagnostic metric-provenance models.
- Update all workspace/app versions to 1.3.0 only when the protocol model builds
  cleanly.

### Phase B — connectivity

- Add a standards-based STUN client path and a persistent Agent QUIC endpoint
  so the discovered mapping and advertised candidate share a socket.
- Publish fresh signed Agent candidates and exchange any Controller candidates
  only inside an authorized Session.
- Rank/deduplicate pairs and run bounded authenticated checks while keeping Relay
  ready. Preserve manual configured-public support.
- Add direct attempt/success/failure/fallback counters without IP-address labels.

### Phase C — reliability

- Add the bounded reconnect state machine and cancellation on explicit end.
- Implement Direct-to-Relay automatic failover behind a connection supervisor.
- Add narrowly scoped recovery credentials/routes only where one-time Relay
  authentication prevents safe rejoin.
- Test sequence continuity, no nonce reuse, stale video dropping, input release,
  and file-transfer ordering across failures.

### Phase D — performance

- Collect real QUIC/path/video data with provenance and setup milestones.
- Extend adaptive video with queue, RTT, decode/render/drop evidence, stability,
  reasoned hysteresis events, and existing encoder bounds.
- Provide Auto, Quality, Balanced, and Low bandwidth profiles with Auto as the
  default while migrating v1.2 settings safely.
- Record reproducible local performance baselines; do not invent results for
  physical network scenarios that were not run.

### Phase E — user experience

- Add a compact localized `P2P Direct` / `Relay` plus quality control to the
  active-session toolbar; opening it reveals diagnostics.
- Localize negotiating, reconnecting, recovered, fallback, and actionable error
  states in Simplified Chinese and English.
- Expand Ctrl+Shift+D diagnostics with only measured/estimated values and em
  dashes for unavailable metrics.
- Refine Settings > Network and perform a constrained consistency/accessibility
  pass using existing design tokens, visible focus, contrast, reduced motion,
  and 1280x720 through 1920x1080 layouts. No new page redesign is planned.
- No Figma source or MCP connection is available for this work, so no Figma
  measurements or components will be asserted; implementation follows the
  existing RemoteX design system and Apple HIG principles.

### Phase F — validation and documentation

- Unit/integration tests for candidate validation/ranking/expiry, state
  transitions, reconnect backoff/cancellation, Relay bounds, adaptation
  hysteresis, quality grading, and diagnostic provenance.
- Targeted Relay idle/pairing capacity tests at 100/500/1000 logical sessions
  where practical without making CI timing-dependent.
- Document and manually execute the available LAN, forced-Relay, transient-loss,
  and local throttle cases. Clearly mark public NAT combinations that require
  two real external networks as not run.
- Update architecture, protocol, security review, connection performance,
  network matrix, measured performance, README, and CHANGELOG.
- Run formatting, Clippy with warnings denied, Rust tests, frontend tests/build,
  release build/package, version consistency, and installer hash generation.

## 4. Primary test matrix and gates

- LAN Host candidate selects authenticated direct QUIC.
- Valid unexpired ServerReflexive candidate is attempted; expired or malformed
  candidates never reach the dialer.
- Direct timeout reaches usable Relay without an unexplained blank delay.
- Direct failure during an active session reaches Relay or a bounded clear
  failure; explicit disconnect never reconnects.
- A recovered session never repeats an E2EE nonce or accepts an old credential.
- Relay rejects oversized frames/invalid credentials/duplicate roles and
  remains bounded under slow or idle peers.
- Diagnostics never substitute placeholder zeroes and do not upload endpoint
  details.
- Both locales contain every new user-facing string; keyboard focus and reduced
  motion remain functional in light/dark/system themes.

The user-facing documentation will keep the four server/path concepts distinct:
Control authorizes and manages devices/sessions; Relay forwards opaque encrypted
fallback traffic; STUN only discovers a public UDP mapping; Direct is the
authenticated peer-to-peer QUIC data path.

## 6. Known constraints at plan time

- STUN improves cone-NAT reachability but cannot guarantee P2P through symmetric
  NAT, carrier-grade restrictions, UDP blocking, or hostile firewalls.
- A server-reflexive mapping is useful only while the exact UDP socket remains
  alive; discovery on an unrelated temporary socket is explicitly out of scope.
- Reliable transparent Relay-to-Direct re-upgrade may be deferred if ordered
  non-video traffic cannot cross a tested synchronization barrier.
- Physical two-network NAT and roaming measurements require an environment not
  present in local CI; their rows will be identified as manual/not run rather
  than reported as successful.
